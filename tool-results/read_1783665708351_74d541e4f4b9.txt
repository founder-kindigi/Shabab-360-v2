     1→# Shabab360 Project Working and Refinement Guide
     2→
     3→Last reviewed: 2026-07-04
     4→
     5→## 1. Purpose of this document
     6→
     7→This document explains how the current Shabab360 project works today. It is meant to help refine the project because the current system is broader than the desired requirements and contains overlapping workspaces.
     8→
     9→Use this document as a baseline. For every module, decide whether it should be kept, simplified, merged, hidden, or removed.
    10→
    11→This document does not store passwords, API keys, or service role secrets. Login credentials should be managed through Supabase Auth or the admin access workspace, not committed into project documentation.
    12→
    13→## 2. One-page summary
    14→
    15→Shabab360 is a browser-based program operations platform for managing Shabab activities across cities, parks, batches, groups, attendance, admissions, fees, content, procurement, and family follow-up.
    16→
    17→The project currently has five main surfaces:
    18→
    19→| Surface | Main routes | Primary users | Current purpose |
    20→|---|---|---|---|
    21→| Public site | `/`, `/apply`, `/apply/status` | Public families | Program entry, admissions application, application status tracking |
    22→| Auth | `/login`, `/reset-password`, `/access-pending`, `/auth/callback` | All users | Email/password login, first-login reset, magic link callback, pending-access state |
    23→| Admin | `/admin/*` | `super_admin`, `program_admin`, `city_head` | HQ and city operations |
    24→| Park | `/park/*` | `park_admin`, `park_lead`, `murabbi` | Park-level attendance and family operations |
    25→| Family portals | `/guardian/*`, `/student/*` | Guardians and students | Read-only personal progress, fees, schedule, announcements, resources |
    26→
    27→The current system is functionally rich but not lean. The biggest product problem is not missing functionality. The bigger problem is that similar work appears across too many pages:
    28→
    29→- Ops Center
    30→- Family Ops
    31→- Attendance Command
    32→- Attendance Alerts
    33→- Attendance Insights
    34→- Fee Alerts
    35→- Access Alerts
    36→- Student Progress
    37→- Park Health
    38→- Batch Health
    39→- Onboarding Center
    40→
    41→For refinement, the main decision is how simple the product should become and which workflows matter most.

   145→student link        -> /student
   146→otherwise           -> /access-pending

   149→## 6. Authentication and access provisioning
   150→
   151→Internal users do not self-register. Accounts are created by admins or scripts.
   152→
   153→Current access model:
   154→
   155→1. A real person or guardian record must exist.
   156→2. Admin opens `/admin/users`.
   157→3. Admin creates or updates an auth account.
   158→4. The account is linked to one of:
   159→   - `people.user_id`
   160→   - `guardians.user_id`
   161→   - legacy `app_users` fallback in some older schema paths
   162→5. Optional first-login password reset is controlled by `user_access.must_reset_password`.
   163→6. User logs in at `/login`.
   164→7. User is routed by role/link state.
   165→
   166→Important current files:
   167→
   168→| File | Purpose |
   169→|---|---|
   170→| `src/lib/auth/guards.ts` | Role landing and server-side guards |
   171→| `src/lib/auth/user-access.ts` | Reads first-login reset/access state |
   172→| `src/features/user-access/data.ts` | User provisioning logic |
   173→| `src/app/api/admin/users/single/route.ts` | Single account create/update API |
   174→| `src/app/api/admin/users/import/route.ts` | Excel import API |
   175→| `src/app/api/admin/users/status/route.ts` | Target access status API |
   176→| `src/app/(admin)/admin/users/page.tsx` | Access management page |
   177→
   178→Refinement concern:
   179→
   180→The system supports both linked target accounts and unlinked accounts. This is flexible but can create confusion. Decide whether unlinked access should remain allowed.

   182→## 7. Database model
   183→
   184→Core hierarchy:
   185→
   186→```text
   187→city
   188→  park
   189→    batch
   190→      group
   191→        participant
   192→```
   193→
   194→Key database tables:
   195→
   196→| Table | Purpose |
   197→|---|---|
   198→| `cities` | Cities in the network |
   199→| `parks` | Parks under cities |
   200→| `batches` | Program batches under parks |
   201→| `groups` | Participant groups under batches |
   202→| `people` | Staff and participants |
   203→| `staff_meta` | Staff role, park assignment, group assignment, city scope |
   204→| `guardians` | Guardian profiles |
   205→| `guardian_children` | Guardian to participant links |
   206→| `batch_settings` | Attendance, fee, and participant-state rules |
   207→| `attendance_events` | Scheduled attendance events |
   208→| `attendance_records` | Per-participant attendance marks |
   209→| `fee_events` | Event-based fee definitions |
   210→| `payments` | Admission/event payments |
   211→| `receipt_sequences` | Receipt number generation |
   212→| `announcements` | Staff, city-head, guardian, and student announcements |
   213→| `report_presets` | Saved report filters |
   214→| `user_access` | Login email and reset-required state |
   215→| `admission_applications` | Public admission submissions |
   216→| `admission_interviews` | Interview schedule and scoring |
   217→| `content_categories` | Resource/content categories |
   218→| `content_items` | Published resources |
   219→| `inventory_items` | Procurement stock catalog |
   220→| `park_allocations` | Inventory allocated to parks |
   221→| `inventory_adjustments` | HQ stock changes |
   222→| `procurement_requests` | Park supply requests |
   223→| `push_subscriptions` | PWA push subscription placeholder |
   224→| `audit_log` | Attendance/payment/auditable changes |
   225→
   226→Important DB behavior:
   227→
   228→- RLS is enabled on operational tables.
   229→- `auth_staff_role()` resolves staff role from the current Supabase user.
   230→- `can_access_park()` scopes data by role and park.
   231→- `guardian_has_child()` limits guardian access to linked children.
   232→- Payment receipt numbers are generated in the database.
   233→- Participant state can be recomputed from attendance streaks.
   234→- Closed attendance events have write restrictions.
   235→- Audit logs record important updates.
   236→
   237→Refinement concern:
   238→
   239→The data model is already broad. Before adding new fields or tables, confirm whether existing modules should be simplified or removed.

   333→## 9. Public admissions workflow
   334→
   335→Current flow:
   336→
   337→1. Family opens `/apply`.
   338→2. Family submits applicant, guardian, city, preferred park, and related information.
   339→3. System creates an `admission_applications` row.
   340→4. A tracking code is generated.
   341→5. Family can check status at `/apply/status`.
   342→6. Admin reviews applications at `/admin/admissions`.
   343→7. Admin can schedule an interview.
   344→8. Admin can record interview status and scores.
   345→9. Admin can approve, waitlist, or reject.
   346→10. Approved applications can be converted into participant and guardian records.
   347→11. Onboarding follow-up appears in `/admin/onboarding-center` and related access/family boards.
   348→
   349→Refinement questions:
   350→
   351→- Is public admission required for the real product?
   352→- Should admissions be a full pipeline or only a simple registration form?
   353→- Is interview scoring required?
   354→- Who approves admission: HQ, city head, or park team?
   355→- Should conversion create both student and guardian accounts automatically?

   463→## 13. Attendance workflow and offline behavior
   464→
   465→Attendance is the strongest specialized workflow in the app.
   466→
   467→Online behavior:
   468→
   469→1. User marks attendance from roster.
   470→2. API validates request.
   471→3. Database upserts attendance record.
   472→4. Participant state can be recomputed.
   473→5. Audit log records important changes.
   474→6. UI refreshes roster.
   475→
   476→Offline behavior:
   477→
   478→1. User marks attendance while offline.
   479→2. Mutation is written to IndexedDB through Dexie.
   480→3. Queue stores event, participant, status, timestamp, mutation ID, and retry state.
   481→4. Auto-sync or manual sync sends mutations to `/api/park/attendance/sync`.
   482→5. API returns processed and failed mutation IDs.
   483→6. Processed items are removed from queue.
   484→7. Failed items remain for retry.
   485→8. Cached event and roster snapshots help keep the screen usable offline.
   486→
   487→Attendance role behavior:
   488→
   489→| Role | Current attendance behavior |
   490→|---|---|
   491→| `park_admin` | Can mark attendance while event is open |
   492→| `park_lead` | Can mark attendance and has more privileged after-close ability |
   493→| `program_admin` / `super_admin` | Can manage broader attendance operations |
   494→| `murabbi` | Park/group-scoped operational access |
   495→
   496→Refinement questions:
   497→
   498→- Should attendance be once per day, or multiple sessions per day?
   499→- Should murabbi be allowed to mark attendance directly?
   500→- Should park admin edit closed attendance?
   501→- Is offline support required for all park roles or only attendance takers?
   502→- What exact statuses are required: present, absent, late, excused?

   653→## 19. Current problems likely causing requirement mismatch
   654→
   655→### 19.1 Too many dashboards
   656→
   657→The app has many dashboard-like pages. This gives many ways to view the same work, but it makes the product hard to explain.
   658→
   659→Likely fix:
   660→
   661→- choose one main action center per role
   662→- convert secondary boards into filters or tabs
   663→- hide low-priority boards from navigation
   664→
   665→### 19.2 Admin and city workflows are mixed
   666→
   667→HQ and city users both live under `/admin`. This is technically fine, but product language may be confusing.
   668→
   669→Likely fix:
   670→
   671→- clearly define HQ vs city duties
   672→- rename nav items to business terms
   673→- remove HQ-only concepts from city navigation
   674→
   675→### 19.3 Student and people modules overlap
   676→
   677→`people` manages Shabab and murabbis. `students` is a student-only view. `student-progress` is another student follow-up view.
   678→
   679→Likely fix:
   680→
   681→- decide whether "People" is the master module
   682→- decide whether "Students" is only a filtered people view
   683→- decide whether "Student Progress" should be a tab inside Students
   684→
   685→### 19.4 Family follow-up is fragmented
   686→
   687→Family concerns appear in guardians, students, access alerts, fee alerts, attendance alerts, family ops, onboarding, and progress pages.
   688→
   689→Likely fix:
   690→
   691→- create one family follow-up workflow
   692→- route all family issues through one page with tabs or filters
   693→
   694→### 19.5 Park workspace may be too complex
   695→
   696→Park users likely need fast attendance and participant follow-up, not a large operations suite.
   697→
   698→Likely fix:
   699→
   700→- reduce park navigation to 4 to 6 top-level items
   701→- place secondary analytics under dashboard or reports
   702→
   703→### 19.6 Some modules may be beyond current requirement
   704→
   705→Procurement, content library, detailed admissions, and many health boards may not be required in the current version.
   706→
   707→Likely fix:
   708→
   709→- mark nonessential modules as phase 2
   710→- hide them until business process is confirmed

   841→
   842→Do not add new modules until the target product shape is confirmed.

   844→### Step 2: Mark every route
   845→
   846→For each route, mark:
   847→
   848→- keep
   849→- rename
   850→- merge
   851→- hide
   852→- remove

   857→
   858→```text
   859→Park Admin:
   860→login -> dashboard -> today's attendance -> roster -> sync -> family follow-up

   862→
   863→If a route does not support a main workflow, move it to secondary navigation or phase 2.

   868→
   869→- merge `Ops Center`, `Family Ops`, `Access Alerts`, `Fee Alerts`, and `Attendance Alerts` into fewer action queues
   870→- merge `Students`, `People`, and `Student Progress` into a cleaner people workflow
   871→- merge `Attendance Command` and `Attendance Insights` into attendance operations or reports
