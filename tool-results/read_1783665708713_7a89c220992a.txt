     8→## 1. Introduction
     9→
    10→### 1.1 Purpose
    11→
    12→This Software Requirements Specification describes the expected behavior, users, modules, data, constraints, and quality requirements for Shabab360.
    13→
    14→The document is written as a refinement baseline. It reflects the current implemented project and identifies requirements that must be confirmed because the existing product is broader than the desired final system.
    15→
    16→### 1.2 Scope
    17→
    18→Shabab360 is a web-based program operations system for managing Shabab activities across cities, parks, batches, groups, attendance, admissions, fees, communications, reports, and family follow-up.
    19→
    20→The current product includes:
    21→
    22→- public homepage and admissions
    23→- internal admin workspace
    24→- park operations workspace
    25→- guardian portal
    26→- student portal
    27→- role-based login and routing
    28→- Supabase-backed data model
    29→- offline attendance support
    30→- Excel reports
    31→
    32→The target refinement should decide which implemented modules remain in scope for the next usable version.
    33→
    34→### 1.3 Intended audience
    35→
    36→This document is for:
    37→
    38→- project owner
    39→- product decision makers
    40→- developers
    41→- UI/UX designers

    72→## 2. Overall Description
    73→
    74→### 2.1 Product perspective
    75→
    76→Shabab360 is a role-based operations portal built on Next.js and Supabase. It is not a public social platform. It is an internal and family-facing program management system.
    77→
    78→The system currently supports a broad operational suite. The refined version should become simpler, with fewer overlapping boards and clearer workflows.
    79→
    80→### 2.2 Product functions
    81→
    82→The system currently provides these top-level functions:
    83→
    84→- authenticate users
    85→- route users by role
    86→- manage cities, parks, batches, and groups
    87→- manage staff, Shabab, and guardians
    88→- create and manage access accounts
    89→- accept public admission applications
    90→- review, interview, approve, and convert admissions
    91→- create attendance events
    92→- mark attendance online and offline
    93→- monitor attendance alerts and insights
    94→- configure batch rules
    95→- track fees and payments
    96→- publish announcements and resources
    97→- manage procurement items and park requests
    98→- show guardian and student portals
    99→- export reports
   100→- review audit logs
   101→
   102→### 2.3 User classes
   103→
   104→| User class | Description | Current access surface |
   105→|---|---|---|
   106→| Super Admin | Technical full-access recovery role | `/admin` |
   107→| Program Admin | HQ program operator | `/admin` |
   108→| City Head | City-scoped operator | `/admin` |
   109→| Park Admin | Park operations user | `/park` |
   110→| Park Lead | Park operations lead | `/park` |
   111→| Murabbi | Mentor tied to park/group work | `/park` |
   112→| Guardian | Parent/guardian linked to child records | `/guardian` |
   113→| Student | Participant with personal portal | `/student` |
   114→| Public Family | Unauthenticated admissions applicant | `/apply`, `/apply/status` |
   115→
   116→### 2.4 Operating environment
   117→
   118→| Area | Requirement |
   119→|---|---|
   120→| Browser | Must support current Chrome, Edge, Safari, and common mobile browsers |
   121→| Device | Must support desktop and mobile layouts |
   122→| Hosting | Current deployment target is Vercel |
   123→| Database/Auth | Current backend is Supabase |
   124→| Offline | Attendance marking should work offline where required |
   125→| Timezone | Pakistan date behavior should use Asia/Karachi |
   126→
   127→### 2.5 Design and implementation constraints
   128→
   129→- The frontend uses Next.js App Router and TypeScript.
   130→- Supabase Auth is the identity provider.
   131→- Supabase Postgres is the system of record.
   132→- Authorization must be enforced server-side and by RLS where applicable.
   133→- Service role keys must not be exposed to client code.
   134→- Internal users must not self-register into privileged roles.
   135→- Attendance offline state is stored locally in IndexedDB.
   136→- Reports are currently Excel based.
   137→
   138→### 2.6 Assumptions
   139→
   140→- The program structure remains city -> park -> batch -> group -> participant.
   141→- Each participant belongs to one group at a time.
   142→- Each guardian can be linked to one or more participants.
   143→- Park attendance is a core workflow.
   144→- Role-based access is required.
   145→- Some current modules may be hidden or removed after requirements confirmation.
   146→
   147→### 2.7 Dependencies
   148→
   149→- Supabase project availability
   150→- Vercel deployment environment
   151→- Valid Supabase keys in environment variables
   152→- Browser local storage and IndexedDB for offline attendance
   153→- Email/password or magic-link access flows through Supabase Auth

   171→

   175→- Given a Guardian signs in, when linked to a guardian record, then they land on `/guardian`.
   176→- Given a Student signs in, when linked to a participant record, then they land on `/student`.
   177→- Given a user has no role or link, when they sign in, then they land on `/access-pending`.

   615→| Access student portal | No | No | No | No | No | No | No | Yes |

   617→| Manage parks/batches/groups | Yes | Yes | City scoped | No | No | No | No | No |
   618→| Manage people | Yes | Yes | City scoped | Limited | Limited | Limited | No | No |
   619→| Manage access accounts | Yes | Yes | Scoped | No | No | No | No | No |
   620→| Create attendance events | Yes | Yes | City scoped | Park scoped | Park scoped | To Confirm | No | No |
   621→| Mark attendance | Yes | Yes | City scoped | Park scoped | Park scoped | To Confirm | No | No |
   622→| View own linked child data | No | No | No | No | No | No | Yes | No |
   623→| View own student data | No | No | No | No | No | No | No | Yes |
   624→| Export reports | Yes | Yes | City scoped | To Confirm | To Confirm | No | No | No |
   625→
   626→This matrix needs final approval before refactoring navigation and guards.
   627→
   628→### 7.2 Access rules
   629→
   630→- The system shall deny by default.
   631→- The system shall enforce role checks in server-side route guards.
   632→- The system shall use RLS for scoped database access where applicable.
   633→- The system shall separate UI visibility from true authorization.
   634→- The system shall prevent guardians from reading unrelated child data.
   635→- The system shall prevent students from reading other student data.
   636→- The system shall prevent park users from writing outside their allowed scope.
