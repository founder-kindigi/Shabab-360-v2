     9→     9→## 1. Project Overview
    10→    10→
    11→    11→Shabab360 is a browser-based, multi-role program operations platform for managing Shabab (youth) activities across cities in Pakistan. The organization runs regular sessions at local venues called "parks," organized into batches (time-bound cycles) and groups (participant cohorts).
    12→    12→
    13→    13→### Core Organizational Hierarchy
    14→    14→
    15→    15→```
    16→    16→National HQ (Markazi)
    17→    17→  └── City (City Masoul)
    18→    18→        └── Park (local venue)
    19→    19→              └── Batch (program cycle, e.g., Jan-Jun 2025)
    20→    20→                    └── Group (15-20 participants + 1 Murabbi/mentor)
    21→    21→                          └── Participant (Shabab - the youth)
    22→    22→```
    23→    23→
    24→    24→### Roles
    25→    25→
    26→    26→| Role | Code | Landing Workspace | Primary Job |
    27→    27→|------|------|-------------------|-------------|
    28→    28→| Super Admin | `super_admin` | Admin | Technical recovery, full access |
    29→    29→| Program Admin | `program_admin` | Admin | National oversight, city governance |
    30→    30→| City Head | `city_head` | Admin | City-level ops: parks, batches, people, events, fees |
    31→    31→| Park Admin | `park_admin` | Park | Daily attendance marking, mobile-first |
    32→    32→| Park Lead | `park_lead` | Park | Park attendance with broader privileges |
    33→    33→| Murabbi | `murabbi` | Park | Mentor, tied to one group |
    34→    34→| Guardian | `guardian` | Guardian | Read-only view of linked children |
    35→    35→| Student | `student` | Student | Read-only view of own data |

    57→    57→
    58→    58→### 2.2 Critical Architecture Constraint
    59→    59→
    60→    60→**All UI must be served from the `/` route (single `page.tsx`).** The application uses a **Single Page Application (SPA) pattern** with client-side navigation managed by Zustand.
    61→    61→
    62→    62→```tsx
    63→    63→// src/app/page.tsx - The ONLY user-visible route
    64→    64→export default function Home() {
    65→    65→  return (
    66→    66→    <SessionProvider>
    67→    67→      <AppRouter />
    68→    68→    </SessionProvider>
    69→    69→  );
    70→    70→}
    71→    71→
    72→    72→// AppRouter renders different workspaces based on auth state + navigation state
    73→    73→function AppRouter() {
    74→    74→  const { status } = useSession();
    75→    75→  const currentPage = useAppStore(s => s.currentPage);
    76→    76→
    77→    77→  if (status === 'loading') return <LoadingScreen />;
    78→    78→  if (status === 'unauthenticated') return <LoginPage />;
    79→    79→
    80→    80→  return (
    81→    81→    <AppShell>
    82→    82→      <PageRenderer page={currentPage} />
    83→    83→    </AppShell>
    84→    84→  );
    85→    85→}
    86→    86→```

   154→   154→### 2.6 Authorization Pattern
   155→   155→
   156→   156→All authorization is enforced in API routes (server-side), never in the client.
   157→   157→
   158→   158→```typescript
   159→   159→// src/lib/auth/authorize.ts
   160→   160→export function requireRole(allowedRoles: string[]) {
   161→   161→  return async (request: NextRequest) => {
   162→   162→    const session = await getServerSession(authOptions);
   163→   163→    if (!session) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
   164→   164→    const userRole = session.user.role;
   165→   165→    if (!allowedRoles.includes(userRole)) {
   166→   166→      return NextResponse.json({ error: 'Forbidden' }, { status: 403 });
   167→   167→    }
   168→   168→    return null; // Authorized
   169→   169→  };
   170→   170→}
   171→   171→
   172→   172→// Scope helpers
   173→   173→export function requireCityScope(session: Session, cityId: string) { ... }
   174→   174→export function requireParkScope(session: Session, parkId: string) { ... }
   175→   175→```

   749→   749→## 7. Coding Standards
   750→   750→
   751→   751→### 7.1 Naming Conventions
   752→   752→
   753→   753→- **Files:** kebab-case (`attendance-roster.tsx`)
   754→   754→- **Components:** PascalCase (`AttendanceRoster`)
   755→   755→- **Stores:** camelCase with `use` prefix (`useAppStore`)
   756→   756→- **API routes:** kebab-case (`/api/admin/attendance-events`)
   757→   757→- **DB tables:** snake_case (`attendance_records`)
   758→   758→- **DB columns:** snake_case (`participant_id`)
   759→   759→- **Types/Interfaces:** PascalCase (`AttendanceRecord`)
   760→   760→- **Constants:** UPPER_SNAKE_CASE (`ATTENDANCE_STATUS`)
   761→   761→
   762→   762→### 7.2 Component Pattern
   763→   763→
   764→   764→```tsx
   765→   765→// Every page component follows this pattern:

   771→   771→import { LoadingState } from "@/components/layout/loading-state";
   772→   772→
   773→   773→interface SomePageProps {
   774→   774→  // props from parent
   775→   775→}
   776→   776→
   777→   777→export function SomePage({}: SomePageProps) {
   778→   778→  const { selectedParkId } = useAppStore();
   779→   779→
   780→   780→  const { data, isLoading, error } = useQuery({
   781→   781→    queryKey: ["some-data", selectedParkId],

   785→   785→
   786→   786→  if (isLoading) return <LoadingState />;
   787→   787→  if (error) return <ErrorState error={error} />;
   788→   788→
   789→   789→  return (
   790→   790→    <div className="space-y-6">
   791→   791→      <PageHeader title="Page Title" description="Page description" />
