# U01 — unassigned participant intake and assignment

Assigned to: Astra. Module: people-placement. Status: done. Depends on: O01.

## Outcome and boundary

Support a participant who joins before placement. They may remain unassigned,
must not enter group attendance or group-scoped work, and may later be placed in
an active group by an authorized user. The group determines the participant's
park; no park is inferred from personal data.

Safe default: only `super_admin` and `program_admin` with `students.manage` may
create or list an unassigned participant, because it has no hierarchy scope.
For an immediate mid-batch placement, any user with `students.manage` may create
or assign only when the selected active group resolves within that user's city,
park, or group scope. The server derives park and city from the selected group.

The 12 current production records are test data. Preserve them unassigned. Do
not inspect their identities, modify production data, run migrations, deploy,
or alter the established UI in this task's contract stage.

## Contract

1. `Participant.groupId` is nullable in both Prisma schemas; `Participant.group`
   is optional. Existing group-based behavior continues to exclude null groups.
2. `POST /api/admin/students` accepts an optional `groupId`. Without it, only
   the two central roles above may create the record and the response identifies
   it as unassigned. With it, the server resolves and authorizes the selected
   active group's hierarchy before creating the participant.
3. `PATCH /api/admin/students/:id/assignment` accepts exactly one bounded active
   `groupId`. It requires `students.manage`, verifies the caller may manage the
   target group, derives park/city from that group, and writes an audit entry.
   It never accepts a client-provided park/city or silently changes attendance.
4. A central-only unassigned filter returns the existing privacy-safe directory
   projection. Group-based attendance, schedule, reporting and student portal
   queries exclude unassigned records.
