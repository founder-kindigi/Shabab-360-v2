# Architecture
- The Shabab SQLite schema uses `staff_attendance_records` and `staff_attendance_events` tables (not `park_staff_attendance_*`); keep reset-plan/import table references aligned with the actual schema names. Confidence: 0.78
- Derive organization scope server-side from active StaffMeta assignment paths (assignedCityId, assignedParkId, assignedGroupId) on every request; client query params may only narrow, never broaden scope. Confidence: 0.80
- Require HQ roles (Super Admin, Program Admin) to supply an explicit cityId (else 400); scoped actors deriving a foreign/missing city return 403. Never trust session scope as authority - always query active StaffMeta. Confidence: 0.80
- Use dynamic capability gates (server-resolved, e.g. `teams.memberships.manage`, `mashwara.manage`) instead of hard-coded role arrays, both in API authorization and UI visibility; pass capability booleans from server components to clients, never `useSession` role checks. Confidence: 0.80
- Make authorization fail closed: inactive/expired/revoked records deny access; no fallback to mock on operational failure. Confidence: 0.75
- When adding a new validation/eligibility guard to an existing transactional mutation, order it after authorization but before the row lock / optimistic-version check / audit writes so denial fails closed with zero writes; keep the existing authorization, `If-Match` version check, and audit-history behavior intact rather than reordering or replacing them. Confidence: 0.72
- Protect PII: mask/fingerprint sensitive data in reports and logs, expose raw details only to directly assigned/authorized users, redact sensitive fields in audits. Confidence: 0.75
- For any city-scoped list/detail, block unfiltered cross-city results; enforce boundaries before any database query. Confidence: 0.70
- Persisted entity IDs mix CUID (new Prisma rows) and UUID (legacy/reconciled Lahore rows); Zod identifier validators for persisted IDs must accept both formats (z.union([z.string().cuid(), z.string().uuid()])), never CUID-only. Confidence: 0.70
- Off-day/weekday schedule settings are global and module-agnostic (single shared batch-off-days helper); never create per-module off-day configuration. Confidence: 0.70
- To relax a column to nullable in SQLite, rebuild the table under `PRAGMA foreign_keys=OFF`/`defer_foreign_keys=ON` (create a `new_*` table, copy all rows, drop, rename, recreate every index/unique constraint); SQLite cannot alter a column constraint in place. Confidence: 0.65
- Adding a SQLite migration folder requires bumping the hardcoded migration-count assertions in release tests (`master-production-signoff.test.ts`, `pilot-production-health.test.ts`, plus the migration-text-mirror assertion in `src/lib/migrations/production-preflight.test.ts`); keep SQLite and PostgreSQL schema/migration treatment aligned. Confidence: 0.65
- When the SQLite chain cannot express the identical constraint to PostgreSQL (e.g. SQLite cannot add a self-referential foreign key to an existing table without rebuilding it), record the asymmetry as an explicit documented decision with the local workaround named (e.g. the guarded schema reconciler) rather than silently omitting it; the model itself (field nullability, relation, back-relation, index, deletion behaviour) must still match across providers. Confidence: 0.60
- Never edit generated Prisma clients; make preflight/collision checks read-only or disposable-local only, and never create a migration merely to make a test or folder-count assertion pass. Confidence: 0.62
- Prisma active-record lookups keyed on a non-unique field (e.g. `group.findUnique({ where: { id, isActive: true } })`) are rejected by the generated client; use `findFirst({ where: { id, isActive: true } })` instead. Confidence: 0.70
- Guard nullable relations before dereferencing (e.g. nullable `participant.group`): in list projections skip/omit unassigned records (flatMap), and on detail routes return 403 for scoped callers (no leak of an unassigned record) and 409 for central/HQ staff, never throw. Confidence: 0.75
- Fix incorrect displayed metrics by tracing the real data relationship rather than trusting a summary/side field (e.g. a park's batches come from its groups' `batchId`/`batch.name`, not `Batch.parkId` or `_count.batches`); use only existing, approved endpoints/contracts and never invent a new endpoint or chart or fabricate data. Confidence: 0.70
- Preserve API compatibility for existing clients: extend contracts additively (new fields on the existing response) and introduce a dedicated new route only when strictly necessary, never by changing or removing existing fields. Confidence: 0.75
- For a bounded time-series/analytics endpoint, scope it to authenticated authorized management roles, validate `from`/`to` query params against a bounded maximum range (400 on malformed, unordered, or over-long dates), and reject before reading any data. Confidence: 0.75
- Derive a management analytics period from real business data — the active Batch's start date through the latest completed class session that actually has attendance data — never from a rolling day-count window, "today", the configured batch end date, or future scheduled calendar dates. Exclude future dates and scheduled days with no recorded marks from the series, and return an explicit empty/no-session result (e.g. `hasCompletedSession: false`, `periodEnd: null`) rather than a clamped or zero-filled window. Confidence: 0.70
- Keep internal persisted role names stable and expose product-facing labels via one shared derived mapping at the API/session contract edge (added additively, only where role metadata already exists); the label is derived from the role and is never an independent source of truth. In this product `program_admin` presents as "Program Head" and `super_admin` as a technical "System Owner" that is never shown as an operating role. Confidence: 0.70
- Never label an aggregate with one entity's identity when the scope can legitimately span several (e.g. an unscoped Program Head/System Owner view containing several cities and therefore several active Batches): resolve the full set of active entities in scope, return/display a name and period only when exactly one is in scope, and otherwise return an explicit multi-entity state (e.g. `multiBatch: true`, `batch: null`, `batches: [...]`) with a neutral label such as "All active batches" instead of falling back to an arbitrary earliest entity. Keep the scope-wide aggregates accurate in that state. Confidence: 0.68
- Input-validation bounds on a query period (e.g. a 366-day maximum range) apply only to explicit client-supplied `from`/`to`; a server-derived period taken from real business data must be used exactly as stored, with no clamp and no rolling window. Confidence: 0.65
- Make the app shell (e.g. `PwaApp`) the single owner of navigation state — current screen, selected entity, and return destination — and pass explicit callbacks into scoped child views; scoped flows must never fall back to a global store navigation (e.g. `useAppStore().navigateTo()`) for shell routing, and back navigation must return to the recorded origin (attendance opened from a workspace returns to that workspace; workspace back returns to the selector). Confidence: 0.72
- Treat the group-to-park hierarchy rule as authoritative and apply it uniformly to every filter, metric, and displayed park/city label (via the shared helpers, never `Group.batch.parkId` alone): a present `Group.parkId` always wins, and `Group.batch.park` is a fallback only when `Group.parkId` is null. A group whose own park is outside the requested/resolved city or park must never be included merely because its batch park is in scope, and mismatched batch metadata must never leak another city's name into rows or exports. Confidence: 0.72
- A role-scoped flow must use only that role's own server-scoped endpoints: never fall back to a generic admin endpoint (e.g. `/api/admin/parks`) or an unscoped park/group lookup, and never reuse the legacy generic admin detail page as a stand-in for another role's screen. The park/group identity handed to navigation comes solely from the server-scoped response. Confidence: 0.70
- Deactivate accounts rather than delete them on rollback or offboarding (set `users.isActive=false` and `staff_meta.isActive=false` and increment `tokenVersion` to invalidate live sessions), because attendance, audit and operation-receipt history reference the identity; deletion is never used. Confidence: 0.68
- Production account provisioning must be strictly role-scoped and fail closed on missing or inactive scope, with no generic unrestricted "admin" account path: City Head pinned to an active city (never park/group), Program Head organisation-scoped, Park Lead and Murabbi city+park with an optional group (active without one but denied group/attendance data), Park Admin and Muawin city+park and never a group, a Muawin's assistance link must be a same-park Murabbi or teaching Park Lead, Shabab/Guardian are non-staff (created from participant/guardian records and refused by the staff path), and the system-owner `super_admin` identity is never provisionable. Confidence: 0.68
- When a role-scoped screen needs a truthful figure that role's own endpoint does not return, add the smallest server-side, tested, role-scoped response field (derived from that role's own scope/access path) and extend the existing response additively — never fabricate, hardcode, or infer the value on the client (e.g. by reading a generic admin endpoint or defaulting with `|| "City"`/`|| 5`). Confidence: 0.65
