- Isolated module-delivery candidates (e.g. `D:/iBuild/Shabab-360-c0-20260911/n01-notifications-20260914`) are outside the file-tool/`directory` workspace (allowed: `D:/iBuild/Shabab-360-v2`); access them via shell by prefixing commands with `cd /d "D:\\iBuild\\Shabab-360-c0-20260911\\..." && ...`, never via read_file/read_directory. Confidence: 0.70
- When applying type-cleanliness/null-safety edits across routes, first capture the baseline `tsc --noEmit` error list for the affected files, then after edits verify the affected files reach 0 errors so pre-existing unrelated failures (e.g. missing `@testing-library/react`) are not mistaken for regressions. Confidence: 0.70
- Before editing, read the whole task packet, the referenced task doc, AGENTS.md, and the affected code and tests; then fix only *confirmed* defects, backed by synthetic fixtures rather than live data. Confidence: 0.70
- Treat the stated blast radius as hard: for a backend/parser repair, do not touch local/live databases, schemas, migrations, accounts, UI, packages, or credentials unless explicitly in scope. Confidence: 0.72
- In review-driven correction passes, treat the review document (e.g. an "Astra review" of a prior handoff) as the authoritative scope: implement every enumerated correction in one pass, keep previously accepted diagnoses/findings intact, and leave unrelated pre-existing working-tree changes untouched (targeted diff, no opportunistic cleanup). Confidence: 0.72
- Pair every correction with a meaningful, focused test for the specific reviewed behavior (e.g. invalid-date session marking, inactive groups/batches, summary-like participant names, a date-accurate today percentage) rather than leaning on existing coverage. Confidence: 0.70
- Cover each new route/mutation guard with explicitly requested "valid and denied" cases: a happy-path success assertion plus every denial branch (inactive group/batch, unscheduled date, stale version), each asserting the denial returned before any write (no lock, no record read/update, no audit). Confidence: 0.70
- Close each correction pass with a handoff that returns the exact changed-file list and verification results (focused vitest, typecheck, scoped lint, `git diff --check`), plus the API/contract assumptions the change relies on and any enumerated residual/out-of-scope items, for the next review. Confidence: 0.70
- For read-only/aggregate-only safety tasks, prove the "no write" claim with captured before/after fingerprints (file size, `LastWriteTimeUtc`, DB sidecar/journal count, directory file count) around every dry run and test run, and note that the exercised path never opens a database or reads env/connection strings. Confidence: 0.70
- When a fail-closed safety guarantee depends on runtime/library behavior (e.g. whether a read-only open of a missing SQLite file creates it), verify it empirically with a throwaway probe script instead of assuming it. Confidence: 0.62
- Audit a guarded execute path by confirming each safety precondition fails closed (write mode off by default, explicit target/backup-dir flags, read-only schema verification before backup) and that backup → verify → reset ordering is pinned by tests so a failed backup aborts before any destructive step. Confidence: 0.66
- For a gated/destructive operation, deliver preflight-only work without overclaiming: state explicitly that the operation was NOT executed, and return the exact files changed, dry-run counts against the expected aggregates, proof of no write, the owner's later execution command, rollback steps, and remaining risks. Confidence: 0.72
- In the handoff, enumerate exactly which verification was actually performed and explicitly state that browser/device, live-database, build/release, and deployment validation were NOT performed when they weren't; never imply or claim a validation kind that did not happen. Confidence: 0.68
- For bounded clean-code/dead-code passes, detect unused named imports programmatically (PowerShell regex over each file: parse `import { ... } from` groups and flag any imported symbol whose non-import occurrence count is `<= 1`), re-run the detector across source AND tests after edits until `NO_UNUSED_IMPORTS`, and confirm each removal is behavior-preserving by re-running the focused suite, scoped eslint, `tsc --noEmit`, and `git diff --check`. Confidence: 0.65

- When asked for project status or a module-completion audit, expects a deep evidence-based markdown file deliverable (not a chat-only summary) covering every module with explicit status, built features, and remaining/gated work — layered across UI, API, and database/schema, grounded in current code + tests + delivery state/baseline/memory rather than blueprint or old completion claims, plus an honest roll-up and prioritized next-focus suggestions. Confidence: 0.72
- In module/project status reporting, label local lead acceptance distinctly from production, UAT, merge, or release approval ("Done (local)" ≠ release); be honest about partial vs done and never invent features. Confidence: 0.68

Confidence: 0.72
- Before a local database write, create a timestamped backup in the ignored local backup directory, verify it, and report its exact path, the preflight result, aggregate post-write verification, and the rollback command (plus rollback cleanup of any handoff file) in the handoff. Confidence: 0.70

Confidence: 0.68

- Verify a database write independently of the module that performed it: re-query the created record's aggregate facts from the file itself, compare every table's row count against the pre-write backup, and assert only the expected tables changed (no stray sidecar files). Confidence: 0.65
- Deliverable source files must be git-trackable: never leave a new module/test under a `.gitignore` pattern (e.g. `local-*`) so the feature cannot be committed or reproduced — fix an ignore defect by renaming the files to non-ignored names and updating every importer, never by editing `.gitignore`; confirm with `git check-ignore -v` (no output/exit 1) and `git status` showing them untracked. Confidence: 0.72
- Keep a CLI's usage text/header docs exactly in sync with its implemented argument contract: implement a documented flag or remove it from the usage, keep the default preflight read-only with the minimal required args, and retain every explicit execution gate. Confidence: 0.70

Confidence: 0.65
- In a repo whose live local DB is shared with a running dev server, treat unexpected mutations as an external side-effect: prove your own runs touched only OS-temp fixtures, prove the affected account/backup/handoff are unchanged (row facts, byte size, mtime), investigate the writer (audit log, running node/next processes), and flag the external write in the handoff rather than claiming or quietly absorbing it. - For release-preparation / commit-preparation work, default to non-mutating preparation: never commit, push, deploy, or write to a database unless a later explicit owner command authorizes it, and preserve unrelated dirty files. - Data reconciliation/reporting must be reproducible and privacy-safe: report aggregate counts, deterministic hashes, IDs, and explicit mismatch categories; never print participant names, phone numbers, passwords, or private workbook rows. - Never manufacture a passing check: when verification counts, migration histories, or expected aggregates mismatch, report the exact mismatch evidence with concrete blockers, owners, and next commands rather than creating a migration, editing data, or tweaking config/tests just to make the numbers line up. - For cross-database (SQLite → PostgreSQL) migration compatibility preflight, inspect both schemas, migration histories, and existing preflight/reconciliation tooling without ever connecting to an operational PostgreSQL database; state whether a disposable replay can be run safely without environment secrets, and return the required preflight checks plus backup/rollback requirements before any production migration. Confidence: 0.65
- For a not-yet-authorized deployment/pilot, produce a drafted-but-unexecuted runbook covering production backup/integrity confirmation, migration preflight, import/provisioning procedure, role-login and attendance-session smoke tests, rollback decision points and commands, and post-pilot reconciliation — with passwords and private source rows excluded. Confidence: 0.62
- In reconciliation/comparison tooling, canonicalize and hash both sides with the identical function: if one side emits raw business keys while the other emits digests, every item silently reports as unmatched (and the raw keys leak into the report). Assert the shared digest format for both sides with a focused test. Confidence: 0.6
- During a read-only/safety-first task, keep the working tree limited to intentional deliverables: put throwaway probe scripts and intermediate outputs in the OS-temp scratchpad (or delete them right after use), and finish by proving only the intended new files were added and no pre-existing file was modified. Confidence: 0.6
- Stage explicitly by path list only: never `git add .` / `git add -A`, `git commit -a`, `git reset`, `git restore <path>` (working tree), `git clean`, stashing, rebasing, or any force operation. Preserve every unaccepted working-tree change exactly as found, and prove it (compare before/after tracked-modification and untracked counts). Confidence: 0.85
- Commit in small, coherent units: each commit carries exactly one purpose and must pass its own focused tests/lint before it lands, with a clear conventional-commit message (`feat(attendance): …`, `fix(auth): …`). Confidence: 0.8
- Never stage or commit sensitive/local/generated artefacts: any `*.db`/WAL/SHM, backups, DPAPI handoffs, passwords/credentials, `.env`, `tool-results/`, spreadsheets or private source data, throwaway patch/debug scripts, and unrelated UI/schema/migration/package/config changes — the DB file and private workbooks stay uncommitted and untouched. - Review the actual `git diff` of every candidate against its approved scope — do not trust the handoff document alone to justify staging a file. Confidence: 0.75

- Before each commit, verify on the staged set: focused tests, scoped ESLint, the project typecheck command, `git diff --check --cached`, and an inspect of `git diff --cached` — reporting exact commands and exit codes. Confidence: 0.75
